# Data generation

How `src/6-MockExternalSystems/Humaid.RiskGovernance.MockSystems/db/seed.sql`'s synthetic
CRM/Core Banking/Vendor records were produced - the architect's Platform Ecosystem Diagram
explicitly calls for this to be documented ("the prompts that produced [the mock data] get logged
in `/ai` - it's part of what the AI harness judging criterion is looking for, applied to data
engineering, not just app code"). 100% synthetic per the hackathon's own hard constraint - no real
customer, product, or vendor data anywhere in this repo.

## Approach: hybrid, per the architect's doc

**One hand-authored "golden path"** - the highest-editorial-care row in each table (id suffix
`...001`): Meridian Textiles Ltd (Corporate, Bangladesh) opening a Cross-Border Wire Transfer Plus
product, vetted by Global KYC Solutions Inc (a certified Singapore-based KYC vendor). Written by
hand, not generated, specifically so the demo has one reliable, coherent, well-grounded lifecycle
to walk end-to-end (used throughout this project's own verification passes - see the git history
around Phase 3 Step 3/5).

**AI-assisted bulk variation** - the remaining rows, generated by Claude Code (this repo's
designated AI coding tool per `CLAUDE.md`) directly as part of implementing Step 2, following the
brief in [`mock-systems-generation-prompt.md`](mock-systems-generation-prompt.md). Both are
grounded in the same real reference material the rest of this project cites (FFIEC BSA/AML
category definitions, plausible real-world jurisdictions/entity types) rather than being random
noise - "structurally plausible, not just noise," per the architect's own phrasing.

## Deliberate edge cases

Two rows exist specifically to break a case that shouldn't silently pass, not to pad out the
dataset:

- **No clean framework mapping** (`...002` in `crm_customer` / `core_banking_product`) - a
  domestic individual retail customer paired with a cosmetic UI-only process change. Nothing about
  either maps cleanly onto any FFIEC risk category. Used directly by
  `evals/datasets/category_mapping.json`'s `cm-05-no-framework-mapping` case and mirrors that
  same principle in `IChangeRequestService`'s "don't guess when nothing applies" rule.
- **Vendor missing certification** (`...002` in `vendor_registry`) - `certification_status: None`,
  `vendor_risk_rating: High`, a Cayman Islands jurisdiction, and broad data access scope
  (transaction data + card PANs). Deliberately the least-defensible vendor row in the seed set.

## Schema validation / QA review

The architect's doc names this as a QA-owned step (Shanthi, per `CLAUDE.md`'s team table) ahead of
data going into the seed store. In this pass, the equivalent check was: every row satisfies
`schema.sql`'s own `CHECK` constraints (enforced by Postgres at apply time - an invalid
`customer_type`, `certification_status`, etc. fails the `INSERT` outright, not silently), and the
end-to-end verification in Phase 3 Steps 3-5 (submit → ingest → category-mapping grounding →
committee decision → feedback loop) exercised every row referenced by that lifecycle for real
against the running service.

## Regenerating or extending

To add more variety (more edge cases, a second golden-path lifecycle for a different change type),
extend `seed.sql` directly following the same pattern - real-sounding entity names, FFIEC-aligned
category-relevant fields, at least one CHECK-constraint edge worth testing per new batch - and
update this file's edge-case list if the new rows exist to test something specific, not just to
add volume.
