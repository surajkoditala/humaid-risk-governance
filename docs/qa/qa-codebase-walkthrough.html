Unit tests

The only file added to the existing xUnit project.

tests/Humaid.RiskGovernance.AdminUI.UnitTests/Assessment/AssessmentServiceTests.cs
295 lines 12 tests xUnit + Moq US-6.3

Why it exists

AssessmentService.FinalizeAsync is the single chokepoint enforcing CLAUDE.md's central rule. CommitteeService.CastVoteAsync refuses a vote unless the request is already PendingCommittee, so finalization is the only route to a committee decision. It had no test at all. That made it the highest-value thing in the repo to cover.

Internals

1. Type aliases, to dodge a real C# collision

The model class and its namespace share a name (…Models.CategoryMapping.CategoryMapping), which makes an unqualified reference ambiguous. The alias keeps the test body readable:

using CategoryMappingRecord =
    Humaid.RiskGovernance.AdminUI.Infrastructure.Models.CategoryMapping.CategoryMapping;

2. Four mocked repos, one system under test

private readonly Mock<IAssessmentRepo> _assessmentRepo = new();
private readonly Mock<ICategoryMappingRepo> _categoryMappingRepo = new();
private readonly Mock<INarrativeSectionRepo> _narrativeSectionRepo = new();
private readonly Mock<IPolicyResearchRepo> _policyResearchRepo = new();
private readonly AssessmentService _sut;

3. A Given(...) helper that makes each test one readable sentence

Readiness depends on three collections agreeing with each other. Setting all three inline in every test would bury the point, so one helper arranges the world and each test states only what it is varying:

private void Given(
    IReadOnlyList<CategoryMappingRecord> categories,
    IReadOnlyList<NarrativeSection> sections,
    IReadOnlyList<PolicyReliance> reliance)
{
    _categoryMappingRepo.Setup(r => r.GetMappingAsync(AssessmentId)).ReturnsAsync(categories);
    _narrativeSectionRepo.Setup(r => r.GetSectionsAsync(AssessmentId)).ReturnsAsync(sections);
    _policyResearchRepo.Setup(r => r.GetRelianceAsync(AssessmentId)).ReturnsAsync(reliance);
}

Plus three small builders — Category(...), Section(...), Reliance(...) — so a test reads as domain language rather than object construction.

The last readiness test asserts behaviour that is arguably wrong, and says so in its own comment. With zero active categories both readiness loops are no-ops, so IsReady is vacuously true. Rather than quietly "fixing" someone else's module, QA pinned the current behaviour so that any future change to it is deliberate and visible — and raised it as DEF-004. It was later confirmed end to end through the UI.

How we know these tests actually work

A green suite is a claim, not evidence. The gate condition was temporarily replaced with if (false) — effectively deleting the rule — and the suite re-run:

Failed: 5, Passed: 57, Total: 62

Exactly the five FinalizeAsync_* tests failed. The other seven stayed green because they call CheckReadinessAsync directly and never pass through the gate. That selectivity is the signal: a blunt suite would have failed more, or fewer, and told us nothing. Production code was then restored byte-for-byte (git diff -- src/ empty).

The Playwright harness

Configuration, safety guard, and the two fixture modules everything else builds on.

tests/e2e/playwright.config.js
47 lines2 projects

Purpose

Defines two independent projects so the cheap suite does not inherit the expensive one's dependencies. api needs only the API; ui additionally needs the Vite dev server.

projects: [
  { name: 'api', testDir: './api', use: { baseURL: API_BASE_URL,
      extraHTTPHeaders: { Accept: 'application/json' } } },
  { name: 'ui',  testDir: './ui',  use: { baseURL: WEBAPP_BASE_URL,
      trace: 'retain-on-failure', screenshot: 'only-on-failure' } },
]

Decisions worth knowing

  • forbidOnly: !!process.env.CI — a stray .only silently narrows the suite. Fine locally, never in CI.
  • retries: CI ? 1 : 0 — no retries locally, so flakiness is visible rather than masked.
  • trace: 'retain-on-failure' on ui only — a trace is the difference between "step 6 failed" and seeing exactly what was on screen. Too heavy for the API project, which has nothing visual to show.
  • Base URLs come from API_BASE_URL / WEBAPP_BASE_URL so CI overrides config without editing the file.
tests/e2e/global-setup.js
29 linesload-bearing

Purpose — and why it is not merely politeness

Pings /api/Ping before any test runs and aborts the whole run with setup instructions if it fails.

The reason this file exists

Several tests use test.fail() to record known defects. A test.fail() test "passes" when it fails for any reason — including a refused connection. Without this guard, running the suite with nothing listening on :5210 would produce a fully green board that proves absolutely nothing. The guard converts that silent lie into a loud, actionable error.

Verified: with the stack down the run exits 255 and prints the three commands needed to start it. /api/Ping is the right probe because PingController deliberately carries no [Authorize].

tests/e2e/fixtures/users.js
37 linesAPI specs

Purpose

Resolves the six seeded users by role, never by hardcoded id — ids are generated by seed_dev_users.sql, so pinning them would break on every re-seed.

const byRole = (role) => users.find((user) => (user.role ?? user.Role) === role);
return { all: users, productOwner: byRole('ProductOwner'), analyst: byRole('Analyst'),
         committeeMember: byRole('CommitteeMember'), admin: byRole('Admin') };

It throws a diagnostic error rather than returning empty when the table looks unseeded — so "the DB was not set up" never masquerades as "the endpoint returned nothing".

Also exports NON_EXISTENT_ID: a well-formed GUID that deliberately matches no record, used by probes that must be rejected on authorization grounds before any lookup happens.

tests/e2e/fixtures/app.js
86 linesUI specs

Purpose

Everything the browser journeys need: signing in as a role, two selector helpers, and an API shortcut for arranging preconditions.

openAppAs(browser, role) — there is no login to automate

While Auth0 is unconfigured, DevUserContext.jsx reads the acting user straight out of localStorage.devUserId. Seeding that key before first paint is the sign-in — faster and far less brittle than driving a user-picker, and it uses the app's own mechanism rather than a test-only backdoor.

await context.addInitScript((id) => window.localStorage.setItem('devUserId', id), user.id);
await page.goto(WEBAPP_BASE_URL, { waitUntil: 'domcontentloaded' });

const bypass = page.getByRole('button', { name: /Continue without signing in/i });
if (await bypass.count()) await bypass.click();

// Proves the role took effect before any assertion depends on it.
await expect(page.getByText(`${user.displayName} — ${role}`)).toBeVisible();

That final assertion matters: without it, a failure to switch user would surface later as a confusing "element not found" in whatever screen the test expected.

nav(page, label) — a one-line fix for a real trap

export function nav(page, label) {
  return page.getByRole('button', { name: label, exact: true });
}

The sidebar has "Submit Request"; the intake form has "Submit request". Playwright's accessible-name matching is case-insensitive unless exact is set, so without this every nav click is a strict-mode violation resolving to two elements. This cost real debugging time and is exactly the kind of thing worth centralising.

createChangeRequest(title) — arrange via API, assert via UI

Returns the created record ({ id, requestNumber, … }). Tests whose subject is a later stage use this instead of re-driving intake through the browser: faster, independent of journey ordering, and it keeps each test's failure pointing at the thing it actually tests.

Why two passing tests sit in a defect file

The "Input validation still holds" block is deliberate and load-bearing. It proves the API is not simply accepting everything — so the finding stays precisely an authorization gap and is never overstated into "the API is wide open". Keeping the counter-evidence in the same file is what makes the rest of it credible.

The test.fail() pattern

Every defect test asserts the secure behaviour and is annotated test.fail():

test('the user directory is not readable without a credential', async ({ request }) => {
  test.fail(); // DevBypassAuthHandler authenticates every request; returns 200 + all six users.

  const response = await request.get('/api/User');
  test.info().annotations.push({ type: 'actual status', description: String(response.status()) });

  expect(response.status(), 'unauthenticated read of /api/User should be rejected').toBe(401);
});

Three things happen at once. The board stays green while the gap is open. The moment somebody implements role checks, Playwright reports "expected to fail, but passed" — the fix announces itself. And the annotation records the actual status in the HTML report, so the evidence travels with the test.

When a defect is fixed, delete the annotation — not the test.

tests/e2e/ui/governance.spec.js
128 lines3 testsDEF-004DEF-006

DEF-004 — an empty assessment reaches the committee

The most serious finding in the product so far, and the clearest example of the unit suite and the UI suite working together: it was predicted by a characterization unit test, then confirmed in the browser.

CheckReadinessAsync iterates over the active mapped categories. With none mapped, both loops are no-ops and IsReady is vacuously true — so the Finalize tab reports "Ready to finalize."

Verified end to end on 2026-09-12: a change request with zero categories, zero policy reliance decisions, zero extracted fields, zero narrative and zero risk scores was finalized, routed, and appeared in the committee queue with a live "Submit vote" button. The committee is being asked to take an accountable decision on a document containing nothing but a title.

Two tests cover it: one asserts the Finalize tab refuses it; one asserts it never reaches the queue.

DEF-006 — opening a workspace fails the first time, every time

func_getOrCreateAssessment does SELECT-then-INSERT with no ON CONFLICT and no lock:

SELECT id INTO v_id FROM assessment WHERE change_request_id = p_change_request_id;
IF v_id IS NULL THEN INSERT INTO assessment ...

React 18 StrictMode double-invokes effects in dev, so two POSTs race. Both read NULL, both insert, and the loser violates UNIQUE (change_request_id) → Npgsql 23505 → HTTP 500. The row is created, so a second click works.

A test that was written, then deliberately deleted

A browser-level version — click Open, assert no 500 — was written first and removed. It only fails when the two requests genuinely overlap, and it passed on one full-suite run while failing in isolation. A test.fail() marker that oscillates is worse than no test, because it trains everyone to ignore the signal.

The kept version drives the race directly with Promise.all, reproduces 23505 every time, and makes the stronger claim anyway: this is a stored-function defect, not a React dev-mode artefact. Two analysts opening the same request simultaneously would hit it in production, where StrictMode does not apply.

const open = () => fetch(`${API_BASE_URL}/api/Assessment/OpenWorkspace/${change.id}`,
                        { method: 'POST' });
const [first, second] = await Promise.all([open(), open()]);

expect([first.status, second.status],
  'func_getOrCreateAssessment must be idempotent under concurrent callers').toEqual([200, 200]);

Fix for both halves: INSERT … ON CONFLICT (change_request_id) DO NOTHING, then re-select.

57 linesreproducibility

Purpose

Regenerates the strategy report's standalone HTML and PDF from one source, using the Chromium already installed for Playwright — so the PDF never becomes a stale binary nobody can rebuild.

node tools/make-report-pdf.mjs <src.html> <out.pdf> <out.html>

Two details that matter

  • It wraps the fragment. The artifact source has no <html>/<head> — the Artifact runtime supplies that at publish time. A standalone file must carry its own, or it misrenders when opened from disk or attached to an email.
  • It waits on document.fonts.ready. Without this the export silently falls back off IBM Plex and the entire type system is lost — a failure you would only notice by comparing side by side.

Why it is built this way

Five techniques used throughout, each solving a specific failure mode. Worth understanding before extending the suite.

1 · test.fail() for known defects

Assert the correct behaviour, mark the test expected-to-fail. The board stays green while the gap is open; when the fix lands, Playwright reports "expected to fail, but passed" and the fix announces itself. The alternative — deleting the test, or weakening it to match the bug — loses the requirement permanently.

2 · Characterization tests for behaviour that is not ours to change

Where current behaviour is arguably wrong but the fix belongs to another module's owner, pin it with a clearly-commented test. Future change becomes deliberate and visible rather than accidental. DEF-004 was found exactly this way.

3 · Mutation checks, because green means nothing on its own

Break the rule deliberately, confirm the right tests fail, revert. Done for the finalize gate: five failures, precisely the five guarding it. This is the single most useful thing to show a reviewer who asks whether a green suite means anything.

4 · A guard against false greens

global-setup.js exists solely because test.fail() and a dead server are indistinguishable without it. Any suite mixing expected-failures with real infrastructure needs this, or it will eventually report success while testing nothing.

5 · Counter-evidence kept alongside findings

Passing validation tests sit inside the defect file; the "Ping stays deliberately open" test sits inside the authentication block. Both exist so the findings stay precise. Scope claims honestly — the DEF-002 caveat is written into the test file, the README and the report, because a finding that overstates itself gets argued down and takes the true part with it.

If you extend this suite, keep these

Prefer edge cases over golden-path duplicates. Keep the UI suite at three journeys. Name the user story every test proves, in the test's own comment — that is what makes a traceability matrix mechanical rather than a separate invention. And never let a test pass for a reason you have not checked.
