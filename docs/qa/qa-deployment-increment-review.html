New findings

Five issues raised by reviewing this increment. One is a deployment blocker.

DEF-007HighDeployment

There is no path to apply the database schema in Azure

The application is entirely stored-procedure driven — every repository method calls a named func_* routine. Those routines live in src/4-Persistence/…AdminUI.DB/, which is a plain SQL folder, not a compiled project. Three facts together make this a blocker:

  • The Dockerfile never copies …AdminUI.DB/ into the image — verified, zero references.
  • Program.cs has no migration, bootstrap or deploy_all.sql execution on startup.
  • No pipeline applies it — there is no application pipeline at all.

ops/README.md says the Flexible Server uses the "same schema deploy_all.sql already applies locally", but names no mechanism for applying it to Azure. On first deploy the containers will start cleanly and then fail on every request, because not one function exists.

Impact
First deployment to Azure cannot work. Discovered on deploy day, this costs hours the team does not have
Fix options
A schema-deploy step in the release pipeline (psql against the Flexible Server), an init container, or a startup bootstrap guarded to run once
Owner
Suraj (pipeline) with Suleman (schema)
DEF-008MediumArchitecture

The VNet is provisioned but connected to nothing

main.vnet.tf creates a VNet with two purpose-built subnets:

  • snet-cae-dev-01 — a /20 carrying a Microsoft.App/environments delegation, which is exactly and only what a Container Apps Environment needs
  • snet-pep-dev-01 — a /24 with service endpoints for Key Vault, Storage, SQL and Web, i.e. sized for private endpoints

The Container Apps Environment module accepts infrastructure_subnet_id, internal_load_balancer_enabled and vnets_to_link. main.cae.tf passes none of them, and module.vnet is referenced by no other file and no output.

So the network designed for isolation is paid for and unused; the Container Apps Environment remains publicly reachable. There is a second-order effect worth noting: the .checkov.yml suppression of CKV_AZURE_139 (ACR public network access) is justified on the grounds that "agents have no private network path to the registry" — but a private-endpoint subnet now exists, unused, which weakens that justification.

Impact
Cost without benefit; the network-isolation story cannot be demonstrated
Fix
Pass the delegated subnet id into the CAE module, or state explicitly that VNet integration is out of scope and defer the VNet
Owner
Suraj
DEF-009MediumContainer security

Both containers run as root

Neither Dockerfile contains a USER directive, and mcr.microsoft.com/dotnet/aspnet:10.0 defaults to root. Every process in both images therefore runs privileged.

This is the single most commonly flagged container finding, and both Trivy and Checkov detect it (DS002 / CKV_DOCKER_3). Since the team already runs both scanners against Terraform, extending them to images would catch this automatically.

Fix
One line per Dockerfile — USER $APP_UID, which the .NET 10 base images define for exactly this purpose
Owner
Suleman
DEF-010MediumOperations

Observability is wired in code but disabled in infrastructure

main.cae.tf carries this line:

# log_analytics_workspace_id = module.log_analytics_workspace... #disabled for now to avoid costs

Both services already register Azure.Monitor.OpenTelemetry.AspNetCore and activate it whenever APPLICATIONINSIGHTS_CONNECTION_STRING is set. So the application side is ready and the infrastructure side is commented out — meaning a deployed environment would emit no logs, traces or metrics at all.

The cost concern is legitimate and was raised on the team's own architecture call. But Operations is one of the six graded SDLC stages, and "we wired the code and disabled the resource" is a weaker story than a free-tier workspace with sampling. Worth a deliberate decision rather than a commented line.

Owner
Suraj, with a team decision on cost
DEF-011LowContainer hygiene

No HEALTHCHECK, and base images are not digest-pinned

Neither image declares a HEALTHCHECK, and both reference floating tags (sdk:10.0, aspnet:10.0) rather than digests. Container Apps supplies its own probes, so the health check matters less in the target environment than it does for local smoke testing; the floating tag means two builds a week apart can differ silently.

Fix
Add HEALTHCHECK hitting /api/Ping; pin base images by digest once the build is stable
Owner
Suleman

Testing strategy update

The increment adds two layers the existing strategy did not cover.

The strategy so far had four layers — unit, API/authorization, UI journey, AI evaluation — plus one acknowledged gap (database invariants). This increment introduces container and infrastructure as testable surfaces, and makes deployment a thing that can be verified rather than only described.

LayerStatus beforeNowTooling
Unit — service invariants62 testsUnchangedxUnit + Moq
API + authorization12 testsUnchangedPlaywright
UI journeys6 testsUnchangedPlaywright
AI evaluation2 of 12Still blocked on a modelCustom C# harness
Database invariantsGapStill the top gapTestcontainers (not started)
Container image—New — 12 casesdocker build/run, Trivy image scan
Infrastructure as codepartly, in the IaC pipelineNew — 11 casesterraform validate, tflint, Checkov, Trivy
Deployment verification—New — 5 casesSmoke tests against a deployed environment

Principles carried forward

The new layers inherit the same rules that govern the existing suites, because they solve the same failure modes:

  • Assert the correct behaviour, mark known gaps — CT-07 (non-root) and IAC-08 (VNet integration) assert the secure state and are expected to fail until DEF-008/009 are fixed, so the fix announces itself.
  • Never let a dead environment look like a pass — every container and deployment case must first confirm the thing under test is actually reachable, exactly as global-setup.js does for the API suite.
  • Keep counter-evidence — CT-06 (no secret in the image) passing is what makes the DEF-009 finding precise rather than "the containers are insecure".
Priority has not changed

These new layers are valuable, but they do not displace the top recommendation. The audit_event append-only trigger and the CHECK constraints remain unreachable by all 80 existing tests and all 28 new ones — container and IaC tests do not touch application data. Testcontainers is still the single highest-value thing left to build.

A new open question for the team

Q6 — who owns database schema deployment?

DEF-007 is not purely technical; it is an unassigned responsibility. The schema is a first-class deliverable of the application (every repo method depends on a named function), but applying it to a deployed environment is a pipeline concern. Neither owner has claimed it, which is precisely why it fell through. This needs a named owner before the first Azure deploy, not during it.

Existing open questions — unchanged

Q3 (does a scoring override need secondary sign-off?) and Q5 (who approves configuration changes?) remain genuinely open and unanswered in code. Q1, Q2 and Q4 remain resolved. Nothing in this increment touched them.

Traceability

No user story's coverage changed, because no application behaviour changed. The register still stands at 12 of 22 covered, 6 partial, 4 with no coverage. Deployment work does not move those numbers — a point worth making explicitly, because shipping Dockerfiles can feel like progress against the product requirements when it is progress against a different stage entirely.

The honest read on this increment

The deployment work is good and it advances a graded stage that had nothing in it. But across five days the defect count moved from six to eleven, and none of the original six closed.
