01

Scope & ownership

Who tests what, so nothing falls between us and nothing is done twice.

LayerOwnerAnswers
UnitDevIs this class's logic correct in isolation?
APIQADoes the service behave correctly over HTTP, for the right people, in the right order?
DataQADoes the database itself refuse to store something invalid?
UIQACan a real person complete their job end to end?
AI evaluationQAIs the model's output good enough to put in front of an analyst?

Unit testing is out of QA's scope. It belongs with the people who wrote the code and refactor it — it is their safety net, and splitting ownership of it would slow everyone down. Dev currently has 62 unit test cases, all passing, and QA treats them as a given rather than re-proving the same ground.

The rule that prevents duplicated effort

Every check happens at the cheapest layer that can actually see it. API tests never re-assert scoring arithmetic — unit tests do that in milliseconds. UI tests never check a status code — a browser is the most expensive possible way to read one. Each layer only covers what the layers beneath it structurally cannot reach.

03

The four test layers

What each one proves, and why it exists separately.

API tests Playwright · 12 today

The workhorse. No browser, runs in seconds, and it is where authorization actually lives. Four questions per write endpoint:

  1. Happy path — correct input produces the correct result
  2. Bad input — a blank override reason, an out-of-range value, an unsupported file type is refused
  3. Wrong person — a Product Owner cannot cast a committee vote
  4. Wrong time — a vote before routing, a finalize before review, is refused

Data tests Testcontainers · 24 planned

Connects directly to a throwaway PostgreSQL container with the real schema. This is the only layer that can prove the governance rules the product is judged on, because they are enforced by the database rather than by application code:

  • The audit trail is genuinely append-only — UPDATE and DELETE are rejected by a trigger
  • Residual risk can never be stored as zero
  • A mitigation factor of 1.0 is rejected
  • An override without a reason is rejected
  • Every state change writes its audit entry in the same transaction — no silent gaps

UI journeys Playwright · 6 today

Three role journeys — Product Owner raises, Analyst assesses and finalizes, Committee votes — run serially as one story: the same request moving through the workflow. This single path is the product demo and exercises the whole governance chain.

Deliberately small. UI tests need four processes running and are the slowest thing we own, so they answer only the question no cheaper layer can: can a real person complete their job? Twelve is a ceiling, not a target.

AI evaluation 12 cases · 2 executing

Scores the three AI touchpoints — category mapping, document extraction, narrative drafting — against fixed datasets. Deterministic wherever the domain allows: category mapping is scored by exact set-overlap against the FFIEC codes, because the category list is small and fixed.

Narrative quality is scored by a labelled heuristic — citation presence and well-formedness — and the eval documentation says so plainly. A narrative eval that quietly claimed more than it checks would be worse than none.

Where the team can be confident right now

Risk scoring, the committee workflow and intake are solid. Each is covered at two or three independent layers, and the scoring rule that matters most — residual risk can never reach zero — is guaranteed by arithmetic and enforced in three separate places: the formula's own bounds, a C# guard, and a database constraint. That one is not a matter of remembering to check.

Where we are not yet confident, and why

The audit trail and access control are the two real gaps. Both are fixable and both are scheduled. Audit immutability needs the Data layer, which is specified but not yet built — it is the highest-value work remaining. Access control has tests written; they currently record a known gap rather than passing, which is deliberate and explained in section 5.

Policy research has no coverage because it is deterministic full-text search rather than AI, and has been the lowest risk of the ten epics. That is a conscious ordering decision, not an oversight.

05

Why a green board means something

The most reasonable question to ask QA. Three practices answer it.

1 · We break the code on purpose to check the tests notice

A passing test proves nothing until you have seen it fail for the right reason. Before trusting any governance test, we invert the rule it guards and confirm precisely that test goes red — then revert.

Done for the finalization gate: disabling it failed exactly five tests and left the other seven green, because those exercise a different path. That selectivity is the signal. A suite that failed more, or fewer, would be telling us something we did not intend.

2 · Known gaps are recorded as tests, never deleted

Where the product does not yet do the right thing, the test asserts the correct behaviour and is marked expected-to-fail. Three things follow:

  • The board stays green while the gap is open, so it stays readable
  • The moment someone fixes it, the runner reports "expected to fail, but passed" — the fix announces itself
  • The requirement is never lost, which is what happens if you delete the test or soften it to match the bug

This is why some suites show expected failures. They are not broken tests; they are open items with a tripwire attached.

3 · A dead environment can never look like a pass

An expected-to-fail test passes when it fails for any reason — including the server being down. So every suite first confirms its dependency is reachable and stops loudly if not. Without that, a suite run against nothing would produce a fully green board proving absolutely nothing.

And every test names the story it proves 
test('US-8.2 AC5 — a vote is recorded against the member by name', ...)

Both test runners write these names into their results, so traceability back to the Azure DevOps board is produced from a build rather than maintained by hand. A story with no matching test shows up as an empty row on its own.

06

Manual testing

Six scenarios stay manual — not because automation is hard, but because it would answer the wrong question.

ScenarioWhy a human
AI narrative qualityThe eval checks a narrative is well-formed and cites something. It cannot judge whether the citation is apposite or the reasoning sound. That is domain judgement
Examiner-readiness of the audit exportThe requirement is a format "suitable for handing to an examiner". No assertion evaluates that; only reading it does
Exploratory testing of overridesOverride reasons are free text. Scripted tests only find what they were told to look for
First deployment walkthroughSmoke checks confirm services answer. Only a person catches a wrong-but-present environment variable
Accessibility spot-checkScanners catch roughly a third of real problems. The Assessment Workspace is where an analyst lives all day
Committee decision semanticsThe quorum rule is proven. Whether the workflow makes sense to people deliberating is a human question

Each gets a short written outcome recorded — date, who ran it, what they found. A manual pass with no note is indistinguishable from a manual test that never ran.

07

When tests run

Fast feedback on every change; the expensive things later.

StageRunsBlocks the merge?Time
BuildEvery PRYes~2 min
Unit tests (Dev)Every PRYes~1 min
Data testsEvery PRYes~3 min
API testsEvery PRYes~3 min
UI journeysOn mergeSoft at first~5 min
AI evaluationNightlyReport only~3 min

PR feedback stays under ten minutes. That is a design constraint, not an aspiration — a gate slower than that gets bypassed, and a bypassed gate is worse than no gate because it creates false confidence.

UI journeys run on merge rather than per-PR because they need four processes and a browser. Once they have been stable for a week they move to a hard gate.

Current state, stated plainly

The application PR pipeline exists and gates build and unit tests today. The API, Data and UI stages are not yet wired in — the tests exist and pass locally, but they do not run automatically. Closing that is additive: a Postgres service container and three steps. It is the top item on the plan in section 8.

How to read this strategy in one sentence

We test each thing once, at the cheapest layer that can see it; we prove the tests work by breaking the code on purpose; and where we are not yet confident, this document says so rather than rounding up.

Defects

Open findings are tracked separately in the QA defect register and on the Azure DevOps board, each with a reproduction and an owner. They are deliberately not listed here — this document is about how we test, not what is currently broken.

Allowed values, numeric bounds and component boundaries in this document were read from the codebase and the database schema rather than from documentation, so they reflect what the system actually enforces.
