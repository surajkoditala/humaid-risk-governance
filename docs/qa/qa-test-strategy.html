One consequence of the boundary worth naming

Unit testing being Dev-owned is the right call — it is their design, their refactoring safety net. But it is worth recording that DEF-004, the most serious governance defect found so far, was found by a unit test, then confirmed through the UI days later. With QA out of that layer, defects of that shape now depend on the Dev team writing tests for the negative cases of their own invariants.

This is not an argument to change the boundary. It is an argument for the Data layer below to be built properly, because it is the only remaining layer where QA can prove a governance rule independently of the implementation that is supposed to enforce it.

What each layer must not be asked to do

The single most common way a test strategy fails is asking one layer to cover another's ground. The rule here:

  • API tests never assert business arithmetic — that is the unit layer's job and it does it in milliseconds.
  • UI tests never re-prove API behaviour — a browser is the most expensive way possible to check a status code.
  • Data tests never go through HTTP — the whole point is reaching what HTTP cannot.

The three layers

What each covers, with the reasoning for its size.

API layer12 today → ~30 targetPlaywright request

The workhorse. Fast, headless, no browser, and it is where authorization actually lives. Every new endpoint gets API coverage before it gets UI coverage.

Covers

  • Contract — the OperationResult envelope, status-code mapping, response shapes
  • Authorization — role separation across the three roles on every write endpoint DEF-001/002
  • Validation — mandatory reasons, mitigation-factor bounds, supported content types
  • Error handling — unknown ids as 4xx not 500 DEF-003
  • Workflow sequencing — a vote is refused before routing; finalize is refused before review
  • Concurrency — two simultaneous workspace opens DEF-006

Deliberately excluded

Scoring arithmetic and quorum resolution. Both are covered by unit tests in milliseconds; re-asserting them over HTTP buys nothing and slows every PR.

UI layer6 today → ~12 targetPlaywright browser

Deliberately the smallest suite. UI tests are the most expensive evidence per hour in this repo — they need Vite plus both services plus Postgres — and a broad suite would mostly re-prove what cheaper layers already cover.

Covers

  • The three role journeys — PO raises → Analyst assesses and finalizes → Committee votes. This single path is the product demo
  • Governance gates as a user meets them — the Finalize tab refusing an unreviewed assessment DEF-004
  • Override dialogs — that a reason is genuinely mandatory in the UI, not just server-side
  • Role-based navigation — each role sees only its own screens
  • Intake validation — type-specific fields appear and mandatory fields block submission

Growth rule

A new UI test must justify why the API layer cannot prove the same thing. Twelve is the ceiling, not a target.

Data layer0 today → 24 targetTestcontainers + Npgsql

The gap, and the highest-value work left. This layer connects directly to a disposable PostgreSQL container with the real schema applied, and asserts the things the database itself enforces. It is the only place the product's flagship governance claims can be proven.

Aligning tests to user stories

One convention, applied everywhere, which makes traceability a by-product rather than a separate document to maintain.

The convention

Every test names the story and criterion it proves, in the test itself — not in a spreadsheet that drifts. Two forms, one per language:

// Playwright
test('US-8.2 AC5 — a vote is recorded against the member by name', ...)

// Testcontainers (xUnit)
[Fact(DisplayName = "US-9.2 — UPDATE on audit_event is rejected")]

Because Playwright and the .NET test runner both emit the test name into their result files, a traceability matrix can then be generated from a CI run rather than written by hand. A story with no matching test name shows up as an empty row automatically.

Why this matters more than it sounds

The current traceability matrix says 12 of 22 stories covered, 6 partial, 4 with nothing. That was assembled by hand and is already at risk of going stale. Once the naming convention is in place the matrix becomes a build artifact — always current, and impossible to quietly let rot.

Four patterns carried across every suite

1 · Arrange via API, assert via UI

A UI test whose subject is the committee stage should not re-drive intake through the browser. Create the precondition over HTTP in milliseconds, then drive only the part under test. Faster, and a failure points at the thing being tested rather than at setup.

2 · Known defects are recorded, never deleted

Where the product does not yet do the right thing, the test asserts the right behaviour and is marked expected-to-fail. The board stays green, and the moment the fix lands the runner reports "expected to fail, but passed" — the fix announces itself. Deleting the test, or weakening it to match the bug, loses the requirement permanently.

3 · Never let a dead environment look like a pass

An expected-to-fail test passes when it fails for any reason, including a refused connection. Every suite therefore starts by confirming its dependency is actually reachable and aborts loudly if not. Without this, a suite run against nothing produces a fully green board.

4 · Verify the suite by breaking the code

Green means nothing until something has been broken on purpose. Before trusting a governance test, invert the rule it guards and confirm precisely that test fails — no more, no fewer — then revert. This has already been done for the finalization gate and will be repeated for each Data-layer invariant.

Pipeline integration

Where each suite runs, what gates a merge, and what merely reports.

Starting point

No application pipeline exists. Both Azure DevOps pipelines are path-filtered to iac/environments/dev/*, so nothing runs dotnet test, Playwright, or docker build. This section describes what to build, not what to change.

StageTriggerRunsGateBudget
1 · BuildEvery PRdotnet build, npm run buildHard fail~2 min
2 · UnitEvery PRdotnet test (Dev-owned)Hard fail~1 min
3 · DataEvery PRTestcontainers suiteHard fail~3 min
4 · APIEvery PRAPI + Postgres service container, Playwright api projectHard fail~3 min
5 · ImageMerge to maindocker build ×2, Trivy image scan, push to ACRHard fail on HIGH/CRITICAL~5 min
6 · UIMerge to mainFull stack in containers, Playwright ui projectSoft at first~5 min
7 · EvalsNightly + manualAI evaluation harness against FoundryReport only~3 min
8 · Deploy verifyAfter deploySchema/seed check, smoke against the deployed FQDNHard fail~1 min

Total PR feedback: under 10 minutes. That number is the design constraint — a PR gate slower than that gets bypassed, and a bypassed gate is worse than none because it creates false confidence.

Why Data gates the PR but UI does not

The Data suite is fast, deterministic and guards the invariants the product is judged on — it belongs on every PR. The UI suite needs four processes and a browser, is inherently slower, and its failures are more often environmental than real. Running it on merge keeps PR feedback quick while still catching a broken journey before it reaches a demo. Once it has proven stable for a week, promote it to a hard gate.

Reuse what already works

The existing IaC pipeline already installs tooling, handles soft/hard failure cleanly, and runs a Claude review step that posts findings to the PR. Mirroring its structure — including that review step over test results and coverage — makes the application pipeline read as deliberate rather than bolted on, and evidences SDLC automation breadth across stages rather than in one.

Manual validation

Yes — six scenarios genuinely need a human. Each is here because automation would produce a confident answer to the wrong question.

Everything deterministic should be automated, and most of this product is deterministic. But six areas resist it, and pretending otherwise would be the more dangerous choice.

IDScenarioWhy a humanWhen
MV-01 AI narrative quality — read a sample of drafted narratives across all four risk categories The eval harness checks a narrative is well-formed and mentions its citation. It cannot judge whether the reasoning is sound, whether a citation is apposite rather than merely present, or whether an analyst would be embarrassed to hand it to a committee. That is a domain judgement Once per prompt change
MV-02 Examiner-readiness of the audit export — read a full export end to end as if you were the examiner US-9.1 AC3 asks for a format "suitable for handing to an examiner without additional formatting work". No assertion can evaluate that; only reading it can Once per export change
MV-03 Exploratory testing of the override flows — free-text reasons, very long input, mid-edit navigation, double submission Override is first-class everywhere and the input is unconstrained text. Scripted tests only find what they were told to look for; this is where the unexpected lives Timeboxed, twice before submission
MV-04 First deployment to Azure — walk one full change request through the deployed environment Automated smoke checks confirm services answer. Only a human walkthrough catches a broken redirect, a CORS origin missed, or an environment variable that is present but wrong Once, at first deploy
MV-05 Accessibility and usability spot-check — keyboard-only traversal of the Assessment Workspace, contrast, focus order Automated scanners catch perhaps a third of real accessibility problems. The workspace is the screen an analyst lives in all day Once before submission
MV-06 Committee decision semantics — play out reject-with-rationale, defer, and approve-with-conditions with two real people The quorum rule is unit-tested and correct. Whether the workflow makes sense to people deliberating — is the rationale visible to the second voter? does a defer read as a decision or a delay? — is a human question Once, with the team
The line I am drawing

These six exist because a test can only check what it was told to check. MV-01 and MV-02 in particular are where an AI-assisted governance product either earns trust or quietly loses it — and both are exactly the kind of thing a green dashboard will never flag. Everything else in this strategy is automated, on purpose.

How manual results are recorded

Each scenario gets a short written outcome in the test case register — date, who ran it, what they found — so that "we checked" is evidenced rather than remembered. A manual pass with no note is indistinguishable from a manual test that never ran.

The two dependencies outside QA's control

Days 2–4 assume release/1.00 has been merged to main — first raised on 12 September, still not done, and it blocks the entire CI workstream. Days 5–7 assume the Foundry provider is configured. Neither is a QA task, and both sit on the critical path. If either slips past day 5, the corresponding exit criteria will not be met and that should be an explicit, recorded decision rather than a surprise on day 13.
