The project

What is under test, who uses it, and the rules it must never break.

The client is a large national bank. Before any business unit launches a product, adds a feature, changes a process, onboards a vendor, enters a geography or opens to a new customer segment, its Financial Crimes Risk Management (FCRM) function must assess the financial crime risk. Today that runs on email, Word, Excel and SharePoint, takes 15–20 business days, produces inconsistent conclusions between analysts, and leaves examiners reconstructing reasoning by hand.

The Risk Assessment Workbench carries a change request from intake to a committee decision on one governed platform. AI prepares: it maps the request to FFIEC risk categories, extracts structure from submitted documents and drafts the assessment narrative. Humans decide at every step.

The rules the product is judged on

These are the reason the test strategy is shaped the way it is. Each is a must never, and each needs proof at a layer that cannot be bypassed.

  1. The system prepares, humans decide. Nothing is auto-approved, auto-rejected, or allowed past a review gate unreviewed.
  2. Residual risk never reaches zero, at calculation time and at configuration time.
  3. Any AI output can be overridden, with a stated reason, and both the original and the override are kept.
  4. The audit trail is append-only at the data layer, not merely hidden from the UI.
  5. Risk categories come from a real, citable framework (FFIEC BSA/AML), never invented by the model.
  6. Synthetic data only. No connection to a real bank system, and no real mailbox.

02

In scope & out of scope

Stated explicitly, so an untested area is a decision on record rather than a surprise.

In scope — QA owns

  • Functional behaviour of Epics 1–10 and 14 against their acceptance criteria
  • API contract, validation, error mapping and workflow-order rules on all 46 endpoints
  • Database-enforced governance: audit trigger, CHECK constraints, reason guards
  • The three role journeys end to end in the browser
  • AI output quality for category mapping, extraction and narrative (evaluation harness)
  • Human-in-the-loop gates: every AI output reaches the committee only through a review
  • Role-based access (Epic 11) at the API, not just the UI
  • Examiner-ready audit export (US-9.3), content and completeness
  • Mock-system integration and behaviour when a mock system is down
  • SLA tracking and breach email (Epic 19), as it is built
  • Deployment smoke checks on the dev Container Apps environment
  • Security gates in the pipeline: dependency, static and image scans (reviewing results)

Out of scope — and why

  • Writing unit tests — Dev owned; QA consumes the result (39 test methods today)
  • Load and performance at bank scale — a hackathon workload; only response-time sanity is observed
  • Penetration testing — automated scanners only; no adversarial engagement
  • Real integrations — CRM, core banking and vendor systems are mocks by rule
  • Real email delivery — breach mail is captured in a local inbox, never sent
  • Auth0, Azure AI Foundry and Azure platform behaviour — trusted as managed services; only our integration with them is tested
  • Model internals — we evaluate outputs, not weights, training or provider latency
  • Cross-browser and mobile — Chromium desktop only
  • Disaster recovery, backup restore, localisation
  • Infrastructure-as-code correctness — owned by DevOps through the Terraform PR pipeline
The rule that prevents duplicated effort

Every check happens at the cheapest layer that can actually see it. API tests never re-assert scoring arithmetic — unit tests do that in milliseconds. UI tests never check a status code. Each layer only covers what the layers beneath it structurally cannot reach.

API — 1-API

The workhorse layer. Four questions for every write endpoint:

  1. Happy path — valid input gives the correct result inside the OperationResult envelope.
  2. Bad input — a blank reason, an out-of-range value, an unsupported file or a malformed GUID is refused with a 4xx, never a 500.
  3. Wrong person — a Product Owner cannot vote, finalize or change configuration; the actor comes from the token, never the body.
  4. Wrong time — a vote before routing or a route before finalize is refused.

1 · We break the code on purpose to check the tests notice

A passing test proves nothing until it has been seen to fail for the right reason. Before any governance test is trusted, the rule it guards is inverted locally and exactly that test must go red. Done for the finalization gate: disabling it failed exactly five tests and left the rest green. That selectivity is the signal.

2 · Known gaps are recorded as tests, never deleted

Where the product does not yet do the right thing, the test asserts the correct behaviour and is marked test.fail(). The board stays readable, the requirement is never softened to match the bug, and the day a fix lands the runner reports "expected to fail, but passed" — the fix announces itself. Ten of the eighteen QA tests are such tripwires today.

3 · A dead environment can never look like a pass

An expected-to-fail test also "passes" when the server is down. So global-setup.js confirms the API answers before any test runs and aborts loudly if it does not. A suite run against nothing must never produce a green board.

4 · Every test names the story it proves

test('US-8.2 AC5 — a vote is recorded against the member by name', …)

Both runners write these names into their results, so traceability back to the Azure DevOps board comes out of a build, not a spreadsheet. A story with no matching test shows up as an empty row on its own.

Deterministic versus probabilistic

Anything with one right answer is tested with an exact assertion: scoring, quorum, SLA due dates, constraints. Only model output is evaluated statistically, and the narrative eval is labelled a heuristic because it checks form rather than judgement. No LLM is used to grade anything a plain assertion can decide.

Epic 19 — how SLA tracking will be tested

Designed now so the stories are built testable. The confirmed rules — business days, an Admin-maintained holiday calendar, defaults of 2 / 8 / 5 / 15, and the clock pausing during a Product Owner clarification — all have exact answers.

  • Due-date arithmetic (unit): a table of submit times across weekends, holidays and clarification pauses, each with its expected due date. Time is injected through TimeProvider, so no test waits on a real clock.
  • Configuration (API + data): zero, negative and blank targets refused; a reason required; a new version written; an in-flight request keeps its pinned version.
  • Breach email (API): mail is captured by a local Mailpit inbox and read back through its API. Exactly one email per request per stage; the content carries no scoring rationale.
  • Humans decide (API): after a breach, the request's status, assessment and committee decision are byte-for-byte unchanged.
  • Audit (data): SlaBreached and NotificationSent rows are appended, never updated.

  • All data is synthetic. Seeds provide six users covering four roles, the FFIEC framework, a policy corpus, workflow rules, and mock records (six customers, five products, four vendors).
  • Each test creates what it needs and never depends on another test's leftovers, except the three role journeys, which deliberately share one request because that is the story being proven.

  • AI evals use fixed datasets in evals/datasets/, versioned with the code, so a score change is attributable to a prompt or model change rather than to data drift.

PR feedback stays under fifteen minutes, dominated by the AI review. A gate slower than that gets bypassed, and a bypassed gate is worse than none because it creates false confidence.

Stated plainly

The CI pipelines that deploy to dev run no behavioural tests, and no pipeline collects coverage. A green deploy today means "it built, it scanned clean and it started", not "it works". Wiring the API suite and a post-deploy smoke closes most of that gap for little effort.

The strategy in one sentence

We test each thing once, at the cheapest layer that can see it; we prove governance rules at the layer that cannot be bypassed; we prove our tests work by breaking the code on purpose; and where we are not yet confident, this document says so rather than rounding up.
