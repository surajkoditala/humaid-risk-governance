How to read this

Conventions, ID scheme, and what each status actually means.

Status vocabulary

StatusMeaning
PassExecuted; actual matched expected.
Known defectExecuted; actual did not match expected, and that mismatch is a raised defect. Marked test.fail() in code so the suite stays green while the gap is open — and reports "expected to fail, but passed" the moment it is fixed. These are failures, deliberately recorded.
BlockedCould not execute. Currently only the AI eval cases, which need a configured model. Reported as Skip, never as Pass — "we did not check" is not the same claim as "it worked".

Stability

The Playwright suite was run three consecutive times end to end: 18 passed on every run, no flakes. The unit suite was run four times across the session with identical results. One test was written and then deliberately removed for being inherently flaky — see OBS-3.

Suite integrity — the mutation check

A green suite is a claim, not evidence. The finalization gate was deliberately broken (if (!readiness.IsReady) → if (false)) and the unit suite re-run:

Failed: 5, Passed: 57, Total: 62

Exactly the five FinalizeAsync_* cases failed — UT-AS-01 through UT-AS-05 — while the seven readiness and delegation cases correctly stayed green, because they call CheckReadinessAsync directly and never traverse the gate. Production code was then restored byte-for-byte and the suite returned to 62/62.

What narrative scoring does not verify

EV-NR-02 confirms the model returned a non-empty, parseable response — nothing more. It does not independently verify that the model avoided fabricating a claim. Observations

What running these 92 cases actually taught us, beyond the pass/fail counts.

OBS-1 · The unit suite predicted a defect the UI later confirmed

UT-AS-11 was written as a characterization test — pinning behaviour that looked wrong but belonged to another module's owner. Days later, UI-GV-01 and UI-GV-02 confirmed the same defect end to end in the browser, with a committee member able to vote on an empty assessment. The two suites found the same thing from opposite directions, which is the strongest form of corroboration available without a formal proof.

OBS-2 · Green means nothing until you have broken something on purpose

The mutation check is the single most useful artefact in this register. Deleting the finalization gate failed exactly five cases — not four, not fifteen. That precision is what distinguishes a suite that tests behaviour from one that merely exercises code.

OBS-3 · One test was deleted for being flaky, and that was the right call

A browser-level version of UI-GV-03 passed on one full-suite run and failed in isolation — the race only fires when the two StrictMode requests genuinely overlap. A known-defect marker that oscillates is worse than no test, because it trains the team to ignore the signal. It was replaced with a deterministic Promise.all version that also makes the stronger claim: the defect is in the stored function, not in React.

OBS-4 · Counter-evidence is what makes findings credible

API-AU-02, API-AU-06 and API-AU-07 all pass, and all sit deliberately inside the defect file. They prove the API does authenticate one route by design, does validate the mitigation factor, and does reject malformed input. Without them, DEF-002 reads as "the API is wide open" — an overstatement that would get argued down and take the true part with it.

OBS-5 · The largest coverage gap is structural, not an oversight

The audit_event append-only trigger and the CHECK (residual_rating > 0) constraint are the repo's flagship governance claims, and not one of these 92 cases can reach them. No HTTP endpoint attempts an UPDATE audit_event, so no API or UI test can ever exercise that trigger, and unit tests mock the database away entirely. This needs a Testcontainers suite, and it is the top priority.

OBS-6 · The role model exists and is honoured only in the UI

The frontend filters navigation by role — a Product Owner never sees the Committee Queue. The API enforces none of it. That combination is worse than having no role model, because the product looks access-controlled to anyone evaluating it from the screens.

OBS-7 · Two environment issues would break a fresh clone

  • ops/setup-local-db.sh assumes psql on the host. On a Docker-only machine it fails partway; both schemas had to be applied through docker exec instead.
  • The control table is created but never seeded (DEF-005), so GET /api/Scoring/Controls returns [] for every category and US-7.1 AC3's explainability requirement cannot be met.

The honest summary

Of 22 user stories, 12 are covered, 6 partially, and 4 have no coverage at all. The most consequential gap is US-9.2 — the immutable audit trail, this product's flagship governance claim — which no test in this register can reach. That is a structural limit of the current suites, not an oversight, and closing it is the top recommendation.
