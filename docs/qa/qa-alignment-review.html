The verdict

Partially aligned — and the misalignment is a coordination gap, not a disagreement.

What is genuinely good

The new application pipelines are better engineering than I specified. The AI review derives its verdict deterministically from the findings rather than trusting the model's own word, runs Claude with read-only tools and an explicit deny-list so the OAuth token cannot be read out of /proc, treats the diff as untrusted input against prompt injection, and posts inline PR comments only on lines GitHub will actually accept. It also adds SCA and SAST scanning, which my strategy did not ask for. None of that is box-ticking.

Where it does not line up

The pipeline gates the one layer the Dev team owns — unit tests — and none of the three QA owns. API, UI and Data tests do not run. Of the 80 automated tests in the repo, 62 execute in CI and 18 do not, and the 18 are the ones that cover authorization, the human-in-the-loop gates and the end-to-end journeys.

This is not a dispute about method. The pipeline work and my strategy document appear to have been written in parallel over the same few days, so the strategy was never an input to the pipeline. The fix is additive: a Postgres service container and three steps. Nothing already built needs to change.

Two of my earlier findings were independently closed, which matters — it means the loop works when the finding reaches the right person.

Why this matters more than the numbers suggest

The 18 tests that do not run are not a random 18. They are the ones that prove DEF-001, DEF-002, DEF-003, DEF-004 and DEF-006 — every open defect that has an automated reproduction. A pipeline that runs 62 of 80 tests sounds like 78% coverage; in practice it means every known defect passes CI silently.

The methodology

Five principles the QA suites are built on. Worth understanding before extending them, because each solves a specific way test suites go wrong.

1 · Each layer tests only what the layers below cannot

The commonest way a test strategy fails is asking one layer to cover another's ground — which doubles cost and halves clarity about what actually broke.

LayerOnly it can reachMust never do
UnitBusiness logic in isolation, in millisecondsTouch I/O
APIStatus mapping, authorization, the HTTP contractRe-assert scoring arithmetic
DataTriggers, CHECK constraints, transactional atomicityGo through HTTP
UIWhether the screens compose into a workflowRe-prove API behaviour

The clearest example: no endpoint anywhere attempts UPDATE audit_event, so no API or UI test can ever exercise the append-only trigger. US-9.2 — the product's flagship governance claim — is reachable only from the Data layer. That is why the Data layer is not optional.

2 · Known defects are recorded, never deleted

Where the product does not yet do the right thing, the test asserts the right behaviour and is marked expected-to-fail. Three things follow: the board stays green while the gap is open; the moment someone fixes it the runner reports "expected to fail, but passed", so the fix announces itself; and the requirement is never lost, which is what happens if you delete the test or weaken it to match the bug.

3 · Green means nothing until you have broken something on purpose

Before trusting a governance test, invert the rule it guards and confirm precisely that test fails — then revert. Done for the finalization gate: replacing the condition with if (false) failed exactly five tests and left the other seven green, because those call the readiness check directly and never traverse the gate. That selectivity is the signal. A suite that fails more, or fewer, is telling you something different from what you think.

4 · Never let a dead environment look like a pass

An expected-to-fail test passes when it fails for any reason — including a refused connection. So every suite first confirms its dependency is reachable and aborts loudly if not. Without that guard, running the suite against nothing produces a fully green board proving absolutely nothing. This is why the API suite has a global-setup that pings before anything else.

5 · Tests name the story they prove

test('US-8.2 AC5 — a vote is recorded against the member by name', ...)

Both runners emit test names into their result files, so the traceability matrix becomes a build artifact rather than a spreadsheet someone has to maintain. A story with no matching test name shows up as an empty row automatically. This is also what lets the new pipeline's PublishTestResults step do double duty — it is already publishing the data a matrix would be generated from.

And one thing deliberately not automated

Six scenarios stay manual because automation would answer the wrong question confidently — most importantly AI narrative quality (the eval harness checks a narrative is well-formed and cites something; it cannot judge whether the citation is apposite or the reasoning sound) and examiner-readiness of the audit export (US-9.1 asks for a format "suitable for handing to an examiner" — only reading it can assess that).

Closing the gap

Additive only — nothing already built needs changing.

All four missing layers need the same one thing the pipeline lacks: a database. Azure DevOps service containers provide it in three lines.

resources:
  containers:
    - container: pg
      image: postgres:16
      env: { POSTGRES_PASSWORD: postgres, POSTGRES_DB: risk_governance_db }
      ports: [ '5432:5432' ]

# ... after the existing '.NET Unit Tests' step:

  # HARD GATE: data layer — triggers and CHECK constraints (US-9.2, US-7.1)
  - script: dotnet test tests/…IntegrationTests -c Release --logger trx
    displayName: 'Data Tests (Testcontainers)'

  # HARD GATE: API + authorization (DEF-001/002/003)
  - script: |
      psql -h localhost -U postgres -d risk_governance_db \
           -f src/4-Persistence/…DB/deploy_all.sql
      dotnet run --project src/1-API/… &
      cd tests/e2e && npm ci && npm run test:api
    displayName: 'API Tests (Playwright)'

The UI project needs the Vite dev server too, so it belongs on the merge pipeline rather than the PR one — keeping PR feedback under ten minutes, which is the design constraint. A gate slower than that gets bypassed, and a bypassed gate is worse than none.

A second benefit, free

That psql … deploy_all.sql line is also the proof-of-concept for DEF-007. Applying the schema in CI is the same operation the release pipeline needs against the Azure database. Solve it once for tests and the deployment blocker is most of the way solved too.
